# SprayTrace — Memory Sheet

Everything in the project as short, memorisable facts. For questions outside the pitch.

---

## 1 · Identity

- SprayTrace = explainable attack reconstruction for authentication logs.
- Microsoft Innovate 2026, Problem #22, Team MacroHard, ID 244, Bennett University.
- Live on Azure Container Apps, East Asia region.
- One line: normalize → 4 detectors → fusion → gate → campaigns → explained alert.

## 2 · The problem

- Attackers leave traces in authentication logs.
- A big organisation generates tens of thousands of log lines daily.
- Basic tools count failures per account. Catches loud attackers.
- Password spray inverts the shape: one password, 500 accounts, once each.
- No account fails twice. The counter never trips. Invisible.
- The attacker only needs one account out of 500.
- If the defender counts per IP, the attacker spreads across 25 IPs.
- Second problem: alert fatigue. 1,300 alerts helps nobody.
- An analyst needs "29 incidents, this is the worst, here is why."

## 3 · The core insight — the most important thing you know

- Any statistic computed **per source** can be defeated by spreading across sources.
- So our 4th detector has **no source in its grouping key**.
- It groups by **time window alone**.
- The question it asks: in this hour, are many accounts each failing once or twice,
  from many individually unremarkable addresses?
- Rotating IPs cannot evade a window-level question.

## 4 · Dataset — synthetic, ours

- **Not Kaggle. Not downloaded. Generated by `generate_data.py`.**
- 11,229 events. 100 users. 167 source IPs. 9 countries.
- 14 days: 20 September – 3 October 2026.
- 1,719 failures total.
- 1,295 attack events (11.5%), 9,934 benign (88.5%).
- 84 distinct scenarios.
- Breakdown: 1,180 spray, 97 brute force, 18 impossible travel.
- Seed 42 everywhere — `random`, `numpy`, `IsolationForest`.

## 5 · Why synthetic — the defence

- No public dataset has labelled sprays + usernames + source IPs + geolocation together.
- Our detectors need all four.
- LANL: has user, source, success/fail, time. **No IP, no geo, no spray labels.**
- UNSW-NB15: network flows, ports, packets. **No usernames at all.**
- LogHub: infrastructure logs, not authentication.
- The only way to get ground truth is to plant it yourself.
- Without ground truth, no precision or recall figure is possible.

## 6 · Hard negatives — why precision means anything

- Four benign scenarios built specifically to fool our own detectors.
- **Corporate NAT** — many users, one shared office IP. Looks like spray.
- **Legitimate flight** — successes implying ≤ 900 km/h. Looks like a travel attack.
- **Typo failures** — 1–3 failures then a success. Looks like a mini brute force.
- **VPN egress change** — abrupt country change, plausible timing.
- Without these, every detector scores 1.00 on data containing only attacks.
- That number would prove nothing.

## 7 · Schema — 10 fields

- `timestamp` — UTC, window membership, Δt for speed.
- `username` — grouping key.
- `source_ip` — grouping key.
- `country` — distinct-country feature.
- `city` — display, evidence text.
- `latitude`, `longitude` — haversine.
- `success` — failures feed spray and brute, successes feed travel.
- `device_id`, `user_agent` — device change, NAT disambiguation.
- Coordinates assigned at generation → **no GeoIP service, no network dependency.**

## 8 · Ground truth isolation

- Separate file: `data/raw/ground_truth.csv`.
- Four columns: `event_id`, `attack_label`, `attack_type`, `scenario_id`.
- Read by **exactly one file**: `evaluate.py`.
- Never joined to features. Never a model input.
- A separate file makes leakage **structurally hard**, not a matter of discipline.
- A test asserts labels never appear in the event file.

## 9 · Normalisation

- Everything becomes one shape before any detection.
- UTC conversion, type coercion, renaming.
- **Bad rows quarantined, not guessed.** Missing timestamp / username / IP → dropped.
- A fabricated timestamp corrupts every window it touches.
- **Unknown success = failure.** That is the direction that cannot hide an attack.
- Subtle bug avoided: pandas `astype(bool)` turns NA into `True` — it would silently
  delete a failure from both failure-based detectors.
- Format detected once, in `read_events()`. Nothing downstream knows which arrived.

## 10 · Detector 1 — Brute force, T1110.001

- Many attempts, one account.
- Group by `(username, source_ip)`, rolling 5-minute window.
- Fires when failures **> 5** (θ_B = 5).
- Score = `min(1, (B − θ_B)/θ_B + 0.5)`.
- Graded by margin, so 20 failures outranks 9.
- Saturates at B ≥ 15.

## 11 · Detector 2 — Password spray, T1110.003

- Few attempts, many accounts, one source.
- Group by `source_ip`, 1-hour windows.
- Two conditions, **both** required:
  - Breadth: **> 12** distinct accounts (θ_U = 12).
  - Shallowness: **≤ 3** attempts per account.
- **SprayScore = distinct accounts ÷ total attempts.**
- Near 1.0 = spray-like. Near 0.0 = brute-force-like.
- **Why SprayScore alone is useless:** one failed login = 1 ÷ 1 = 1.0, the maximum.
  Every typo would look like the worst spray in the dataset.
- So SprayScore only grades severity **after** breadth is satisfied.
- Each hour evaluated **twice** — on the hour, and offset 30 minutes.
- Reason: an attack from 10:45–11:15 would split across bins and fall under the
  threshold in both. An attacker will not align to our clock.

## 12 · Detector 3 — Distributed spray, T1110.003

- The one we are proudest of.
- 24 addresses hitting 60 accounts = 2–3 accounts per IP = under threshold everywhere.
- The fix is structural: **remove source from the grouping key.**
- Four conditions:
  - ≥ 25 accounts (breadth).
  - ≥ 8 sources (distributed).
  - ≤ 3 attempts per account (spray-shaped).
  - ≤ 12 attempts per source (**each source individually unremarkable**).
- The last condition prevents double-reporting — if one source is loud, the
  per-source rule already covers it.
- Both spray detectors ship because they cover each other's blind spots.

## 13 · Detector 4 — Impossible travel, T1078

- One account, two places, impossible speed.
- Per user, successes in time order, consecutive pairs.
- Haversine great-circle distance ÷ time = implied speed.
- Fires above **1000 km/h**.
- An airliner cruises at ~900 km/h, so 1000 is the boundary.
- Tagged **T1078 (Valid Accounts)**, not T1110 — this is not guessing. The
  credentials already worked. Someone else has them.
- Example: Delhi → London, 3 h = 6711 km = 2237 km/h → fires.
- Same pair, 8.5 h apart = 790 km/h → does not fire.
- Guards: require Δt > 0, skip missing coordinates.

## 14 · Isolation Forest

- Unsupervised. **Never shown which events are attacks.**
- Learns normal, flags what sits far from it.
- Intuition: random recursive splitting. Normal points take many splits to isolate.
  Anomalies separate immediately. **Anomalies are easy to isolate** — hence the name.
- `n_estimators=100, contamination=0.01, random_state=42`.
- 6 features: failures last hour, distinct IPs last hour, distinct countries last day,
  hour_sin, hour_cos, device change.
- **Cyclic hour encoding:** a raw hour makes 23:00 and 01:00 look 22 hours apart.
  Map onto a circle with sin/cos so late night wraps to early morning.
- **Strictly backward-looking.** An event uses its past, never its future. A model that
  sees forward scores beautifully in test and fails in production.
- **Rescaling constants frozen at fit time**, stored with the model. Recomputing them on
  the scored data would make output depend on how many attacks are present.
- `contamination` only affects `predict()`. Our `score_samples` path does not depend on
  it — which is why the 0.01 / 0.02 sweep changes nothing.
- **Never raises a standalone alert.** It contributes to fusion only.

## 15 · Fusion — why the obvious way breaks

- The natural approach: a weighted average with weights summing to 1.
- With 5 signals at 0.2 each, the best possible case is a perfect rule plus a perfect
  anomaly score: `0.2 + 0.2 = 0.400`.
- **0.400.** High starts at 0.60, Critical at 0.80.
- A maximally obvious, perfectly corroborated attack could **never** reach either.
- The tier system would be decorative.
- This is not a bad choice of weights — it is an **arithmetic property of a convex
  combination**.
- Because the weights sum to 1, no detector can pass a threshold unless its own weight
  exceeds that threshold.

## 16 · Fusion — what we do instead

- A fired rule **enters at its own floor**.
- Brute 0.45, spray 0.45, distributed 0.45, travel **0.41**.
- Travel is lower because geolocation is the noisier signal.
- The remaining headroom to 1.00 is **earned** through corroboration:
  - 40% how far past threshold the rule sits.
  - 40% anomaly model agreement.
  - 20% a second, different detector firing on the same event.
- Formula: `R = entry + (1 − entry) × corroboration`.
- A lone moderate rule stays Medium → review queue.
- A strong rule plus anomaly plus a second detector reaches Critical.
- **The floor is NOT scaled by the detector's score.** If it were, a genuine 1342 km/h
  travel would be 0.41 × 0.825 = **0.338** → below gate → suppressed → never seen.
- Confidence belongs in the headroom, not the entry point.

## 17 · Decision gate

- Critical ≥ 0.80 → escalate with evidence.
- High 0.60 – 0.80 → escalate.
- Medium 0.40 – 0.60 → analyst review queue.
- Low < 0.40 → suppressed, audit log only.
- **Suppressed ≠ deleted.** Queryable at `/api/audit`.
- A gate that silently discards data is a **claim**. A gate you can inspect is a
  **control**.
- If we ever miss a low-scoring campaign, the audit log is where it would be found.
- We built the place our own failures would show up.
- Thresholds are **operating policy**, tuned on validation — not universal security
  constants.

## 18 · Campaign reconstruction

- Turns a wall of alerts into something human-readable.
- Groups by shared source, overlapping target set, and time proximity.
- Correlation window 60 minutes, minimum 2 events per campaign.
- **A rotating-IP attack stays ONE campaign**, because correlation keys on the target
  set, not just the source.
- Guard rail: cross-source joins must interleave within 10 minutes of cluster start.
- Without it, two independent attacks sharing one victim would chain into one
  misleading mega-incident.
- Result: **11,229 events → 1,329 above gate → 29 campaigns.**

## 19 · Evidence

- Every campaign carries a sentence built from **the numbers that triggered detection**.
- Generated inside the detector, next to the computation.
- **The explanation structurally cannot drift from the detection** — there is no second
  code path that could describe it differently.
- Example: *"38 failed attempts across 20 distinct usernames (1.9 per account,
  SprayScore 0.53) from 203.0.113.159 within 59 minutes — consistent with password
  spraying (T1110.003)."*
- Every alert carries a MITRE ATT&CK ID.
- This lets output slot into existing SOC workflows instead of inventing a private
  vocabulary.

## 20 · Test protocol

- Split by **whole scenario** — every event of a campaign lands in one split.
- Otherwise half a spray is in training and half in test: testing on an attack it has
  already seen.
- Grid search **27 configurations** on validation only.
- **Freeze** the config into `configs/thresholds.yaml`.
- Measure **once** on held-out test. No tuning afterwards.
- Reporting a number tuned on the same data it is measured on is the fastest way to
  lose credibility.

## 21 · Results — headline

- Baseline: P 1.000, R 0.240, **F1 0.388**.
- SprayTrace: P 0.967, R 0.996, **F1 0.981**.
- The baseline has perfect precision but finds **under a quarter** of attacks.
- It catches brute force and misses everything else — because spray is built to evade
  exactly those counters.
- **3,894 test events → 240 escalatable → 5 campaigns.**
- **91.1% noise reduction**, measured in campaigns because that is the unit an analyst
  opens.
- Comparing raw alerts would show negative reduction purely because we detect more real
  attacks.

## 23 · The three honest results — rehearse these

**Per-source spray scored 0.000.**

- Test scenarios rotate across 20–28 addresses.
- Every single source falls below θ_U.
- Not a bug — it is the exact blind spot the distributed detector exists to cover.
- The clearest possible evidence that both detectors are needed.
- Only visible because we measured them separately.

**Isolation Forest contributed nothing.**

- D scores 0.000. Full fusion (F) exactly equals rules-only (E).
- Honest reading: on synthetic data whose attacks our rules already encode, the model
  adds tier separation but no new coverage.
- Its value would appear against behaviour nobody wrote a rule for — which is, by
  definition, not in data we generated ourselves.
- Reported, not tuned away. Risk #3 in our report.

**Travel precision 0.727 — the false positives are correct detections.**

- A planted travel attack puts the victim in an attacker's city.
- The victim's real background traffic continues from their office.
- The detector pairs the attacker login with the victim's next genuine login and
  reports a real impossible speed.
- Ground truth labels only the two planted events.
- **We did NOT fix this by widening labels.** Relabelling benign events until the metric
  improves is how synthetic evaluations become meaningless. Risk #1 in our own report.

## 24 · LANL external validation

- **3,000,000 real authentication events.**
- Los Alamos National Laboratory internal corporate network, de-identified, 58 days.
- 20,036 failures, 14,290 users, 5,820 source computers.
- Per-source spray: **994 alerts = 0.0331%**.
- Distributed spray: **0 alerts = 0%**.
- **It fired zero times on three million real events.**
- **Proves:** we do not carpet-flag real traffic. A detector firing on 5% of a real
  network is unusable regardless of synthetic recall. Our own generator could never have
  told us this.
- **Does not prove:** that the 994 are false positives. LANL labels only lateral
  movement, not spraying. They are **unverified, not confirmed wrong**.
- Likely cause: service accounts and authentication servers legitimately touching many
  identities — the NAT collision we listed as risk #4, appearing in real data exactly
  where we predicted.
- The travel detector **cannot run** on LANL (no geolocation) — skipped rather than fed
  fabricated coordinates.

## 25 · Entra integration

- Accepts a Microsoft Entra ID sign-in export directly.
- Format detected from the header row.
- `ResultType` `"0"` = success. Everything else = failure.
- **50126** = invalid username or password — the code a spray generates.
- Microsoft Sentinel's own spray analytics use 50126 among their credential-failure
  codes.
- The mapping handles portal, Graph and Sentinel connector spellings.
- Portal exports put "City, Country" in one column — the split is handled, with a guard
  so a bare "GB" does not become city = GB.
- Detection is identical for both sources.

## 26 · Stack and deployment

- Python 3.13, pandas, scikit-learn.
- FastAPI backend. React + TypeScript (strict), Vite, Cytoscape.
- Docker multi-stage, Azure Container Apps.
- **Local vs Azure: zero detection difference.** Same image, thresholds and code path.
- On Azure one container serves API **and** dashboard — single unit, no CORS.
- Data is generated **at build time**, so every container starts byte-identical.
- `min-replicas 1` keeps it warm — no cold start during a live demo.
- **The local path is primary.** `./run.sh` runs everything with no cloud dependency.
- Throughput **5,450 events/sec** — 1M events ≈ 3 minutes.
- **47 tests passing.**

## 27 · Limitations — say these before they ask

1. The primary evaluation is synthetic. Controlled measurements, not a claim about live
   tenants.
2. The Isolation Forest adds no coverage on this data.
3. Travel precision is measured against an incomplete label.
4. Shared IPs remain hard. NAT genuinely looks like spray. Mitigated, not solved — LANL
   showed it in real data.
5. Thresholds are tuned for this dataset. A real deployment needs recalibration.
6. **No real-time streaming.** Batch analysis. Fine for scheduled runs, but not a stream
   processor.

## 28 · Sentinel and the cloud-native future

- Sentinel's built-in spray rules are **per-source**, counting 50126.
- Our distributed detector fills the gap their per-IP rules leave.
- SprayTrace is a **complement, not a replacement**.
- Integration path: a custom analytic rule or connector.
- Gains: live ingestion, retained history, Logic Apps playbooks (auto-disable account,
  force MFA), threat intel enrichment, enterprise scale.
- Caveat: thresholds would need recalibration on real tenant traffic.

## 29 · Traps — what NOT to say

- **There are 4 detectors, not 3.** If asked for "the three techniques," name brute
  force, spray and travel — then add that spray has two detectors.
- **No regression models anywhere.** If a judge says "your regression model," correct
  it: three deterministic rules plus one unsupervised Isolation Forest.
- Never claim the ML layer improved results. It did not, and the reason is interesting.
- Never claim LANL's 994 alerts are false positives. Say unverified.
- Never say the dataset is from Kaggle.
- Do not claim real-time. It is batch.
